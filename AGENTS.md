# Project rules

- The AdTool Agent (Meta Muse Spark 1.3) lives in `supabase/functions/_shared/muse/` and must stay free of Lovable-specific APIs — so the same service can later run on an external host. See `docs/adtool-agent-muse.md`.
- Async agent continuation runs via `agent_tasks` + `agent-task-resume` (cron, restricted tools, atomic claim) — never by keeping a browser request open; `/agent?conversation=` loads from the DB.
- Agent conversation/operation state lives in `agent_conversations` / `agent_messages` / `agent_operations`, never in UI state — the backend owns continuity and cost accounting.
- Paid agent tools price from the canonical `_shared/videoPricingCatalog.ts` and dispatch through the existing `generate-*-video` Edge Functions with the caller's JWT — never re-implement pricing, wallet deduction or provider calls.
- Agent campaigns (Phase A) live in `agent_campaigns` + `campaign_*` tables, written only server-side by the free tools in `_shared/muse/campaign/` — planning never touches pricing, wallet or generation; web assets default `reference_only`; plans fail closed if the semantic duplicate check can't run.
- Campaign social research lives in `campaign_social_profiles` (one row per Instagram/TikTok/Facebook/YouTube), written only by `discover_social_profiles`/`record_social_analysis` in `_shared/muse/campaign/social.ts`; login walls are `not_accessible`, never bypassed, and `agent_campaigns.social_research_complete` is true only when all four platforms are analyzed/not_found/not_accessible — so the agent can never claim a full social analysis it did not do.
- Campaign budget `spent_total` is net successful charges minus refunds; active reservations are tracked separately and count with net spend only for budget availability, never as spend — so reserve→charge cannot double-count.
- Campaign shot QA is claimed/failed/finalized only via the claim_shot_qa / fail_shot_qa / finalize_shot_qa RPCs (lease, retryable qa_pending, stats once per generation) and reconciled by agent-task-resume without a Muse turn — so a finished video never stays 'generating' and QA re-runs never double-count.
- Shot QA stats count once per generation via qa_stats_contributions (partial unique on valid); bad reviews are retired with invalidate_shot_qa (subtracts only that contribution, archives the verdict), never deleted — so one buggy review can be corrected without touching other stats. Review-only copies live under ai-videos/<user>/qa-derived/ and never replace the original video_url.
- Phase B sets only visual readiness (`campaign_shots.visual_client_ready`, derived from `client_ready`); `campaign_videos.final_client_ready` is written only after composition + final QA, and post-production intent (voiceover, music/SFX, overlay text, CTA) is persisted in `post_production` — so the finished ad is never called ready from a raw clip.
- `prepare_shot_retry` plans via pure `_shared/muse/campaign/retryPlan.ts` (failure classes → raised risk → re-ranked router with failed-model penalty → structured prompt rewrite) and refuses wording-only retries (`TRIVIAL_RETRY`) — so a retry always changes something material.
- Agent chat associates approvals/tasks with the user turn by timestamp (`src/lib/agentStatus.ts` groupByTurn); only pending, unexpired approvals render in chat, the rest live in the campaign panel's approval history — so old approvals never look like answers to new questions.
- Every non-internal agent turn persists an assistant row; when no answer is produced it is an explicit `tool_calls.turn_status='interrupted'` row, never fabricated text — so a reload never shows an unanswered request as if it were fine.
- Shot and campaign status in the UI is derived from real jobs via `deriveShotStatus`/`deriveCampaignActivity`, never from the approval row's status; campaign amounts render in the funding wallet's currency (they are stored without one) — so the UI never claims production is active or swaps currencies.
- Agent turns are read-only when the server's `turnPolicy.classifyReadOnly` says so (a client `readOnly` flag can only turn it on); read-only turns expose and execute only `READ_ONLY_TOOLS` — so a missing or forged flag can never unlock paid, approval or writing tools.
- Agent turns are idempotent per (user, requestId) via `agent_request_ids` (same id + other content → 409 REQUEST_ID_REUSED) — so double clicks, reloads and restarts never run a turn twice.
- Shot retries need a `kind='retry'` approval whose `retry_binding` pins campaign, shot, attempt, exact provider request and retry-plan fingerprint (`campaign/retryBinding.ts`), consumed once via `consume_retry_approval`; approval scope and limits are frozen by trigger — so an old or altered approval can never pay for a new attempt.
